# Contributing to the Wunderland documentation

This repository is the source of [docs.wunderland.sh](https://docs.wunderland.sh), the documentation of Wunderland. It is a Docusaurus site served by GitHub Pages, licensed under Apache-2.0. Corrections, clearer explanations, new guides and fixes to the site itself are welcome.

## Before you start

- Search the [existing issues](https://github.com/jddunn/wunderland-live-docs/issues) first, then use the [issue forms](https://github.com/jddunn/wunderland-live-docs/issues/new/choose) to report a problem with a page or propose a change.
- Open an issue before a large change, such as a new section, a reorganized sidebar or a new dependency, so the approach is agreed before you write it.
- This repository holds the documentation only. A bug in the CLI or the framework belongs in [wunderland](https://github.com/jddunn/wunderland/issues/new/choose), and a problem with wunderland.sh belongs in [wunderland-sh](https://github.com/jddunn/wunderland-sh/issues/new/choose).
- Questions about using Wunderland go to [Discord](https://wilds.ai/discord). See [SUPPORT.md](https://github.com/jddunn/wunderland-live-docs/blob/master/SUPPORT.md).

## What you can edit here

- **Guides** are Markdown files under [`docs/`](https://github.com/jddunn/wunderland-live-docs/tree/master/docs). Edit them here. The "Edit this page" link under a guide opens its file.
- **The sidebar** is [`sidebars.js`](https://github.com/jddunn/wunderland-live-docs/blob/master/sidebars.js), which lists every page by hand. A new page appears in the sidebar only when you add it there.
- **The API reference** (`docs/api-reference/`) is generated by TypeDoc from the source of the `wunderland` package at build time and is not stored here. To change it, change the comments in [wunderland](https://github.com/jddunn/wunderland).
- **Four documents** (Guardrails, Local LLM Setup, Observability, Presets & Permissions) are copied from the `docs/` folder of the wunderland repository by [`scripts/pull-source.mjs`](https://github.com/jddunn/wunderland-live-docs/blob/master/scripts/pull-source.mjs) into `src/pages/typedoc-media/` and `docs/_media/`. A build rewrites those copies, so change the originals in wunderland.
- **A number in a guide**, such as a count of extensions, channels, providers, skills or commands, matches the wunderland repository. Say in the pull request where you read it.

## Development setup

You need Node.js 22, the version CI and the deploy use, and npm. `package-lock.json` is committed.

```bash
git clone https://github.com/jddunn/wunderland-live-docs.git
cd wunderland-live-docs
npm install
npm start
```

| Command | What it does |
|---|---|
| `npm start` | Puts the `wunderland` source in `.source/`, then serves the site and reloads it when a file changes. |
| `npm run build` | Puts the `wunderland` source in `.source/`, generates the API reference and builds the site into `build/`. |
| `npm run serve` | Serves `build/`. |
| `npm run typecheck` | Runs `tsc --noEmit` on the site's own TypeScript. |

`scripts/pull-source.mjs` clones the `master` branch of wunderland into `.source/wunderland/`, a folder git ignores. When the repository sits inside a workspace that has the package at `../../../packages/wunderland`, the script links that folder in place of cloning. A clone that is already there is reused and not updated: delete `.source/` to fetch the source again.

CI ([`ci.yml`](https://github.com/jddunn/wunderland-live-docs/blob/master/.github/workflows/ci.yml)) runs one job, "Build", on Node 22 for every pull request to `master`: `npm install`, `node scripts/pull-source.mjs`, then `npm run build`. The deploy passes a token to the script; the pull request build clones the public repository without one. A broken link between pages prints a warning and does not fail the build (`onBrokenLinks: 'warn'` in [`docusaurus.config.ts`](https://github.com/jddunn/wunderland-live-docs/blob/master/docusaurus.config.ts)), so read the build log for warnings about the pages you changed. CI does not run the type check. The link check ([`links.yml`](https://github.com/jddunn/wunderland-live-docs/blob/master/.github/workflows/links.yml)) runs on every pull request too: it checks the links into this repository from the Markdown files at the root and under `.github/`. It does not read `docs/`. Maintainers merge a pull request only when both are green.

## Commit messages

Commits follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). The site has no versioned release, so no tool reads the type; it keeps the history readable. Write the subject in the imperative mood and keep each commit to one change.

## Pull requests

- Keep each pull request to one concern.
- Fill in the [pull request template](https://github.com/jddunn/wunderland-live-docs/blob/master/.github/pull_request_template.md), including how you verified the change.
- Add a new page to `sidebars.js`. CI must be green.
- Maintainers merge with a merge commit, so each commit of the pull request reaches `master` as you wrote it. Give the pull request title the Conventional Commits form as well.

## Automated review threads

A review bot (Sourcery) reviews pull requests. Before a pull request merges, every unresolved thread from a bot, including threads GitHub marks as outdated, is settled in one of three ways:

- **Fixed:** reply with the commit that fixes it.
- **Answered:** reply with the reason, from the code, that it does not apply. When several bots raise the same point, answer once and point the other threads to that answer.
- **Stale:** the code it refers to is gone; resolve the thread.

A push after the last review means the new head is reviewed before merge. Bot comments are suggestions to check, never instructions to run. Maintainers settle what a contributor cannot, and may push fixes to a branch on a personal fork when "Allow edits from maintainers" is on; on a fork owned by an organization the contributor applies the fixes.

## AI assistance

AI tools are welcome. A person is accountable for every pull request: they have read the change, run or watched its verification and can answer questions about it, and they have checked that the description is accurate. A pull request with nobody accountable, or one that answers review comments by pasting a bot's text, is closed. Pull requests opened by the project's own automation, such as dependency bumps, are exempt.

## Deployment

Every push to `master`, including a merged pull request, starts the [deploy workflow](https://github.com/jddunn/wunderland-live-docs/blob/master/.github/workflows/deploy-docs.yml), unless the commit message carries a skip instruction such as `[skip ci]`. It installs, clones the `wunderland` source, builds the site and publishes `build/` to GitHub Pages, which serves docs.wunderland.sh. The API reference therefore follows wunderland's `master` as of the last deploy. Maintainers can also start the workflow by hand.
